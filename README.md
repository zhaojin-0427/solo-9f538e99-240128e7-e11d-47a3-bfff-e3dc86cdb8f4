# 科研就诊明细替码服务

按研究项目接收就诊明细 CSV，用不可逆的替码（PSN- 前缀 + 80 位键控摘要）替换患者号后，交付一份保留行序与其余字段的下载文件。替码表持久保存在数据卷的 SQLite 中，同一研究内一人一码、跨批次复用，不同研究独立分配。

* 输入：UTF-8 CSV，三列依次为「患者号, 就诊 UTC 时间, 诊断码」。
* 输出：UTF-8 CSV，三列依次为「替码, 就诊 UTC 时间(原样), 诊断码(原样)」，行序不变，行尾风格（LF/CRLF）与可选表头原样保留。
* 上限：单个文件 256 MiB；容器内存上限 128 MiB。

## 快速启动

```bash
docker compose up --build -d
# 浏览器打开 http://localhost:8000/
docker compose logs -f          # 查看转换/发布日志
docker compose down             # 停止（数据卷保留）
```

容器以非 root 用户（uid 10001）运行，`research-data` 是命名卷，首次启动时 Docker 会把卷的属主设为该用户；如果你改用宿主目录挂载，请先执行 `sudo chown -R 10001:10001 <宿主目录>`。

数据卷 `research-data` 挂载到容器 `/data`，内含：

| 路径 | 内容 |
| --- | --- |
| `/data/research.sqlite3` | 替码表、研究项目、结果登记（含每个结果的 SHA-256） |
| `/data/secret.key` | 替码派生密钥（首次启动自动生成；也可用 `PSEUDONYM_SECRET` 指定） |
| `/data/results/*.csv` | 已发布的结果文件，只有登记过的文件才会被下载接口提供 |
| `/data/tmp/` | 单批次工作目录，成功或失败后即删除 |

> 密钥丢失会导致无法再现已有替码；请连同数据卷一起备份。`secret.key` 权限为 0600。

## 使用流程

1. 在首页「研究项目」填写名称（同名即同一研究；名称会自动去除首尾空白并折叠连续空格）。
2. 选择 CSV 后提交。整批通过校验才会登记替码与结果；成功后跳到批次详情页，可直接下载。
3. 「结果记录」列出所有批次，可按研究筛选并再次下载。

校验规则（任一行不满足即**整批拒绝**，不给新替码、不留可下载结果）：

* 三列且仅三列；任一列缺失或只有空白字符；
* 任一字段超过 100 个字符（按 Unicode 字符计）；
* 就诊时间必须是合法的 UTC 时刻，接受形如 `2024-05-01T09:30:00Z`、`2024-05-01T09:30Z`、`2024-05-01 09:30:00+00:00` 的写法；非 UTC 偏移、2 月 30 日、25 点等一律拒绝；
* UTF-8 编码（允许 BOM）；不允许空行；单行不超过 8 KiB；
* 文件必须至少有一行数据。

首次上传即自动建档。研究名最长 100 字符。

## 一致性与故障语义

* **新增替码与结果登记共同生效**：结果文件先落盘到随机文件名，再在同一个 SQLite 事务里写入新替码与研究、批次登记；事务提交才对外可见。失败则回滚事务并删除结果文件，工作目录一并清理。
* **并发**：替码由「密钥 + 研究名 + 患者号」键控派生，同一研究的同一患者在任何并发路径上都得到同一替码；登记事务里的校验会在出现不一致时整批回滚。不同研究之间的转换互不阻塞，只有短暂的登记事务串行化。大文件转换期间其他研究的小文件可正常完成。
* **落盘与登记之间中断**：下次启动时删除 `results/` 中没有登记记录的孤儿文件与残留工作目录，已登记的历史结果不受影响、仍可下载（发布与清理之间用 `flock` 互斥，避免误删正在登记的批次）。
* **下载**只对登记过的结果文件名开放，未登记的随机文件即使落在卷里也无法通过 URL 取得。

## 资源占用与容量

实测（本地 waitress，8 线程，Python 3.11）：

* 256 MiB / 7,456,540 行的文件：单批约 90 s（解析 75 s + 登记 13 s），进程峰值 RSS ≈ 47 MiB。
* 在 128 MiB 地址空间硬限制（`ulimit -v 131072`）下完成同一文件，退出时峰值 RSS 29 MiB。
* 两个 256 MiB 上传并发：峰值 RSS ≈ 54 MiB，其间另一研究的小文件上传延迟 < 0.1 s。
* 内存与文件大小无关：上传流式解析，暂存表在磁盘上，行缓存上限 2 万条。

磁盘估算：结果文件与输入大致同尺寸；替码表约 70 B/患者，若重复上传同一批患者不会重复增长。`docker-compose.yml` 里 `mem_limit: 128m`、`memswap_limit: 128m`，并把 `TMPDIR` 指向数据卷，避免把 256 MiB 暂存压进内存。

## 配置

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `DATA_DIR` | `/data` | 数据卷根目录 |
| `PORT` | `8000` | 监听端口 |
| `THREADS` | `8` | waitress 工作线程数 |
| `TMPDIR` | `/data/tmp` | 上传暂存目录（必须可写、磁盘而非 tmpfs） |
| `PSEUDONYM_SECRET` | 空 | 显式指定派生密钥（≥16 字节）；不设则用 `secret.key` |
| `SESSION_SECRET` | 由替码密钥派生 | 仅用于提示消息的 cookie 签名 |

## 本地开发

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
DATA_DIR=./data python run.py         # http://127.0.0.1:8000/
python -m pytest tests -q             # 单元 + 端到端 + 崩溃恢复测试
```

不需要 Docker 时也可直接用 `python run.py` 或 `waitress-serve --call research:create_app`。

| GET | `/` | 上传表单 + 研究列表 + 最近批次 |

## 限制与注意事项

* 替码由「安装密钥 + 研究名 + 患者号」键控派生（BLAKE2b-80），不是随机表；这样并发与崩溃重试天然不会产生两个替码，但持有密钥的人可以验证某患者号是否出现在某研究里，因此密钥必须与替码表一起保护。
* 未提供登录鉴权，请把服务部署在院内受控网络或反向代理之后。
* 时间只做格式与日历校验，不做时区换算；带非零偏移的时间会被拒绝而不是自动换算。
* 结果文件不会自动过期，需要按院内保留策略定期清理数据卷。
